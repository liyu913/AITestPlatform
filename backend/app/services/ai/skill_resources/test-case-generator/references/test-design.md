# 用例质量与数据规范

## 范围与粒度先行

先按 [需求类型与范围](scope-and-granularity.md) 确定覆盖边界和合并粒度。

## 从场景写成可执行说明

一条用例验证一个主要目的，可包含与该目的直接相关的状态和副作用。不要把多个独立业务目标塞入一条，也不要为同一等价类换措辞凑数量。

- 标题说明对象、条件与预期行为；依据、准备状态与标签遵循 [信息不完整也继续设计](../SKILL.md#信息不完整也继续设计)。
- 前置条件说明角色/主体、初始状态、数据关系、依赖和必要配置，并能触发本条要验证的条件；验证单项规则时排除其他限制的干扰，验证交互时明确组合条件。无界面功能使用服务、任务、事件或设备条件，不硬写登录步骤。
- 输入按 [数据准备](#数据准备) 描述场景条件和边界，明确与当前操作的关系。
- 标题、前置条件、步骤和预期尽量使用通俗、准确的表达；必要专业名词首次出现时附简短解释。保留定位或判定所需的字段名、格式、单位及边界值，不为简化措辞改变含义或遗漏关键场景。
- 步骤按实际触发和观察顺序连续编写，不添加“前台／后台／页面／接口”等执行分工标签，也不据此拆分用例或增加列。实际需要发送请求、查看记录或设置故障条件时，直接写清动作和观察点；业务中的真实页面名称和角色照常保留，不把无法从页面验证的结果写成页面可见。
- 无界面功能按请求与响应、事件与完成条件、设备信号与状态等实际行为描述，不能臆造路径、命令或可用工具。
- 预期说明允许/拒绝、输出、状态及数据变化，必要时包括不应改变的对象；每项断言须有对应的准备条件、触发动作和观察点，不能用单对象操作证明多对象一致性。避免“正常”“成功”“符合需求”等空泛判定。
- 必要时说明隔离、清理、恢复和重跑条件。用例设计不要求现在真实创建账号或运行故障注入。

## 编号与对应关系

测试步骤和预期结果分别从 1 连续编号，单条也编号；每个编号项另起一行。两者不要求数量相同，需对应具体操作时写“步骤 N 后……”，不能用操作序号充当结果序号。参数组用 A/B/C 区分，组内数据和结果对应明确。

## 预期结果的判定依据

优先使用明确验收标准、规则计算、契约、可验证的不变量或确认过的业务关系。现有系统输出不能单独证明正确；与旧版本一致也可能复制旧缺陷。

先核对限定词及适用对象：“支持 X”不能推出“拒绝非 X”，“数量不限”不能扩展到其他对象、大小或长度；只有明确的排他约束才能作为已确认的拒绝依据。通用经验推导的约束记录为 inferred，不因看起来合理就升级为 confirmed。

待确认按断言或子规则划分，先回查全文及交叉引用，能直接确定的规则不再提问。“已确认”或“无待确认项”不代表未写出的交互细则已有结论；只保留会改变通过/失败判断、且无法从明确规则推出的最小问题，不把无关实现选择列为待确认：

- 同一流程混有已知和未知结果时，保留已知断言，把未知条件及候选结果明确分开；若验证目的可独立执行，拆为确定用例与待确认用例。
- 未知格式、阈值或生效时点只影响相关分支，不阻断已有依据的成功、失败与恢复检查；准备满足已知条件的受控数据，不用未知边界值承担其他测试目的。
- 追踪文件通过关联的 requirements 和 rationale 说明各断言的来源和依据，无须新增输出列或结构。只要本条通过判定仍依赖未知规则，就保留 conditional/needs_rule，不能因部分结果已知而把整条标为 confirmed/ready。

无法给出唯一结果时，保留测试目的、操作和候选结果/参数化条件。未提供测试账号/环境时保留用例及准备规格，标 needs_data。不要为了得到“可执行”的标签偷偷填入产品规则。

## 数据准备

默认写场景所需的数据条件，例如“有查看权限但无编辑权限的账号”“已有成功版本且来源内容发生变化的记录”，不填虚构账号、仓库地址、业务编号、凭据或提交值，也不把可读的占位符当作已存在资源。用户提供的适用数据可以引用；用户明确要求样例数据、执行数据或自动化夹具时，再按要求准备并注明用途与是否已验证，仍不暴露秘密。

场景描述不等于只写“正常/异常数据”：应保留影响结果的状态、归属、差异和触发条件。格式符号、枚举以及需求已明确的阈值可直接写出；已知上限应给出边界及相邻值，不能因为采用场景写法退化为“符合要求”。

| 情况 | 要求 |
| --- | --- |
| 格式/类别输入 | 描述有效或无效特征，如“缺少域名的邮箱”；仅在判定依赖具体字符时写必要字符，不填看似可用的虚构资源；避免其他条件遮蔽 |
| 数值/时间边界 | 保留需求明确的数值、单位、精度、开闭区间及相邻值，必要时注明时区和时钟来源；未知限制使用 L/T 等参数并记录待确认 |
| 账号/凭据/验证码 | 写角色、权限、有效/失效状态及必要获取条件，不编造用户名、密码、Token或验证码 |
| 多主体/多对象 | 标明 A/B 的角色、状态、归属和关系；明确目标及不应受影响对象 |
| 批量/组合输入 | 给生成规则、规模、唯一性及约束，不要求把大数据全部粘贴进单元格 |
| 故障/并发 | 明确故障点、请求是否可能已提交、参与方及先后关系；未知注入方式写环境待准备 |

使用测试身份和凭据引用，不把真实密码/Token或无必要的个人信息写入产物。无数据要求才写“无”，不能替代未知信息。

## 优先级与测试类型

项目有明确标准时采用项目标准，否则根据失败影响、发生机会、使用频率、恢复成本及传播范围判断。P0 为核心链路阻断或严重数据/权限风险；P1 为重要分支和高风险异常；P2 为一般功能及低风险异常；P3 为低影响边缘或体验问题。边界值不是天然 P2，不追求均匀分布。

内置导出器的一级类型为正常、异常、边界、状态、权限、安全、兼容性、易用性；可追加一致的二级标签。每条只按一个主类型计数。类型分类不限制所采用的方法，也不限制业务领域。

## 按对象选择覆盖维度

常见候选：main_flow（正常执行路径）、alternatives、validation_boundary、state_data、failure_recovery、repeat_concurrency、permission、display、compatibility_usability。不是每个对象必填九类，可按需增加 calculation、event_order、timing 等有明确定义的维度。

基于业务模型与风险记录选择理由。例如纯计算规则重点检查条件组合、精度与结果；事件消费重点检查时序、幂等和恢复，无需浏览器布局；静态说明页重点检查展示与信息准确性，无需虚构保存流程。

行为功能可分类为 action、rule、process、event；都需要真正触发到结果的 main_flow。display 才是纯展示。UI 上能触发行为的入口不能降为 display 来规避主流程检查。

各维度标 covered/partial/uncovered/not_applicable，后面三种说明原因；unknown 不等于 not_applicable。覆盖充分性结合所选方法的具体目标评估，不能只按维度挂一条无关用例。维度遗漏或未选的风险需在选型理由/缺口说明中解释。

## 输出适配
