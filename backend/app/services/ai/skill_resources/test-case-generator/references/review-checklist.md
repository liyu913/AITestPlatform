# 用例评审：找缺口并修复

生成后、导出前使用。先核对原始材料，再检查用例；不能只用生成的清单证明自身完整。区分已有覆盖但表达不清、遗漏独立分支和重复断言：同一目的优先补全原用例，独立目的另列，重复部分按合并规则收敛。发现问题直接修改，重大规则冲突保留待确认，不新增逐阶段审批。

## 先检查范围与粒度

- 需求类型是否有依据？优化有没有只测改动却漏受影响旧行为；新增有没有被错误缩成变更点？
- 每条用例能否对应本次规则、影响或关键风险？移出核心套件的明确要求是否在补充清单中有去向？
- 同规则、同操作的数据是否可参数化？组合后是否仍能逐组判断，不把多个独立状态或业务目标挤进一条？
- 是否为了凑条数或压到固定数量而增删场景？核心安全/一致性风险不能仅因需要接口支持就移走。

## 按功能检查

| 对象 | 必须回答的问题 | 常见修复 |
| --- | --- | --- |
| 操作入口/服务触发 | 是否真正触发并观察结果？目标对象、版本正确吗？ | 补成功路径，按钮存在检查不能替代执行 |
| 可取消交互 | 取消、关闭、返回分别是否提交？材料是否证明该机制存在？ | 已知则写确定用例；未知则写条件用例，不虚构弹窗 |
| 失败恢复 | 失败发生在提交前还是提交后？重试会重复产生副作用吗？ | 分开“明确未提交”和“已提交但响应丢失”，写恢复与核对动作 |
| 重复/并发 | 重复点击、不同主体竞争同一对象、乱序返回会影响什么？ | 只覆盖相关风险，说明先后关系和受影响对象 |
| 状态规则 | 允许迁移、禁止迁移、关键迁移序列是否覆盖？ | 建立状态×事件×守卫表，不能只看状态文字 |
| 授权 | 角色、资源归属、状态、授权变更的允许与拒绝是否覆盖？ | 按实际入口检查服务端结果，不把隐藏按钮当授权通过 |
| 数据 | 输出、持久化、副作用、其他对象隔离如何判定？ | 给独立计算/不变量；未知观察手段记录准备规格 |
| 输入/组合 | 边界单位明确吗？是否被其他错误遮蔽？重要组合是否漏掉？ | 一次改变一个无效因素；条件组合按规则表，不以成对覆盖替代关键业务规则 |

结合 [按对象补充检查](design-methods.md#按对象补充检查适用时) 回查独立可选字段、配置变化、对象关系、多来源分类及规则交互。不适用项给业务理由；没看到不等于不存在。静态页、接口、任务和设备按自身模型选项，不机械补页面交互。

## 按单条用例检查

- 目的：标题说明条件、动作和预期，一条用例只有一个主要验证目的。
- 可执行：角色、初始状态、对象关系、输入特征、动作及观察点明确；默认用场景条件描述数据，不编造地址、账号或业务资源，不以“数据待准备”代替条件。需求明确的边界数值和单位是否保留？
- 表达：术语是否通俗且准确，必要专业名词是否有简短解释？步骤是否按实际操作顺序编写，未加前台／后台／页面／接口分工标签？简化后关键场景、判定条件和必要观察动作是否仍完整？
- 可判定：预期能区分通过与失败，且准备条件和实际操作足以验证每项断言；“正常”“符合要求”不能单独作为结果。
- 依据：按 [判定依据](test-design.md#预期结果的判定依据) 回查材料，消除可直接确定的待确认项，保留影响判定的最小缺口；区分“支持”与“仅支持”，按断言分离已知与未知。推导理由只放追踪文件，不把截图按钮语义或通用经验升级成已确认需求。
- 编号：是否符合 [编号与对应关系](test-design.md#编号与对应关系)，单条及多条都无漏号、跳号或错用步骤序号？
- 独立性：依赖其他用例时改成明确准备步骤或可复用前置条件，避免必须按 Excel 行顺序执行。
- 优先级：按失败影响和风险判断，不设 P0 比例、不按方法固定优先级。
- 去重：比较目的、前置状态/触发时机、规则和结果；按 [合并和拆分](scope-and-granularity.md#合并和拆分) 收敛重复断言，保留独立规则及单点、端到端各自的验证目标，不只比较标题措辞。

## 输出与追踪检查

是否遵循用户选定格式及 [输出约定](output-contract.md)，并正确分离正文标签和追踪信息？每个已选覆盖目标是否对应真实用例或明确缺口，确认过的需求、推导、未知规则是否分开统计？机器校验检查结构、映射、编号和文件一致性；语义覆盖与方法仍需回看材料。补充、合并或收紧验证目标后，同步调整用例与需求/覆盖目标的双向映射，移除已不验证的关联，不能仅凭旧映射继续计为覆盖；只复查受影响规则和导出。

交付给出简短的范围与剩余缺口，不默认输出长篇评分。外部项目的“100%覆盖”“固定条数”“P0占比”不作为质量标准。

## 参考来源与取舍

- [test-case-designer](https://github.com/ll0v0ll/test-case-designer)：借鉴先分析、方法选择与需求追踪；不采用强制逐阶段确认和固定条数。
- [qa-test-strategy-framework](https://github.com/rennanreis/qa-test-strategy-framework)：借鉴把等价类、边界、判定表和状态迁移落到具体例子的方式；不继承演示系统的规则。
- [test-case-studio](https://github.com/2B0748/test-case-studio)：借鉴覆盖、正确性、可执行性、独立性、粒度、追踪、优先级和去重的评审维度；不采用固定 P0 比例或额外列。
- [Casebook](https://github.com/SeldomQA/casebook)：借鉴用例定义与评审、执行记录分离的结构。保留现有 JSON/Excel，不引入管理平台。

上述为思路参考；本 skill 的示例为独立编写的教学材料，不能将参考项目的功能宣传当作验证结果。
