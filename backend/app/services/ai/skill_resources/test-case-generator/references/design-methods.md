# 测试设计方法：从业务模型到用例

## 先确定要覆盖的结构

从材料提取：谁或什么触发、对哪个对象、在什么状态下、输入哪些值、判断哪些条件、产生什么结果、哪些数据应保持不变、依赖哪里可能失败。界面控件只是入口之一；定时触发、服务调用、消息和设备信号同样可以是入口。

为本次对象选择少量适用方法，可以组合但不要求全部使用。记录选择理由和覆盖目标，而非仅列方法名称。先覆盖高影响规则与主路径，再扩展代表性边界/异常；规模与粒度见 [需求类型与范围](scope-and-granularity.md)。

## 方法选择与应用

| 方法 | 何时选择 | 怎样推导 | 覆盖目标与限制 |
| --- | --- | --- | --- |
| 等价类划分 | 输入域、输出域或条件可分成系统处理相同的集合 | 找出有效/无效/缺失/特殊类，为每类取代表；多输入无效时先一次改变一个因素，防止校验遮蔽 | 每个有意义的类有代表；不要把格式相似但处理规则不同的值合并 |
| 边界值分析 | 范围、阈值、长度、数量、时间或精度约束 | 明确区间开闭、单位和步长，取边界及相邻可表示值；必要时覆盖空集、单项、上限 | 双侧边界及分段阈值；金额按最小货币单位、时间按明确精度，不机械全部 ±1 |
| 判定表 | 多个条件共同决定动作 | 列条件、各自取值、约束和结果；枚举可达组合，合并确实无关项，标出不可能组合 | 每个有效规则组合及重要拒绝路径；缺少结果的组合是规则缺口，不能猜答案 |
| 因果分析 | 条件存在依赖、互斥、优先级或连锁动作 | 画出因果/约束，再转成判定表或规则组合 | 防止遗漏依赖和冲突；简单单条件不必画图 |
| 状态迁移 | 行为取决于历史或生命周期 | 列状态、事件、守卫条件、动作、合法/非法迁移；设计可到达前置状态的序列 | 重要状态/迁移、禁止迁移及关键迁移对；循环不无限穷举，明确深度 |
| 场景/用例法 | 多步业务目标、跨模块链路 | 从目标推导成功路径、替代路径、取消/补偿、失败与恢复路径；在节点检查副作用 | 核心路径端到端闭环，不能只验证各按钮独立成功 |
| 组合测试 | 多个参数交互且全组合过大 | 先应用组合约束，强制加入高风险组合，再按成对或更高交互阶数选择覆盖集 | 明确阶数与约束；成对覆盖不证明三因素交互或全部规则正确，不替代高风险判定表 |
| 权限/决策矩阵 | 主体、动作、资源归属或属性影响授权 | 交叉主体/角色、动作、资源关系、状态；包括允许、拒绝、跨主体及权限变更 | 页面/直接调用按实际入口选择；未知矩阵保留条件场景，不虚构接口地址 |
| 数据不变量/关系验证 | 金额、库存、聚合、同步、转换等数据行为 | 给出独立计算或前后关系，例如守恒、唯一性、隔离性、排序/过滤后关系；验证副作用和恢复 | 判定依据必须独立于被测实现；不保证存在的幂等/单调性不能当作既定规则 |
| 错误推测与风险分析 | 依赖失败、历史缺陷、竞态或操作失误 | 在关键节点注入超时/断连/重复/乱序等相关故障；推导可接受结果和恢复方式 | 给出触发条件及业务影响，不散列无关攻击/异常，也不替代系统化方法 |
| 探索式测试章程 | 规则模糊或界面可交互、难以列举所有路径 | 规定探索目标、范围、观察点、记录内容与时间边界；发现规则后转为可复现用例 | 作为补充；章程不能冒充步骤和预期已确定的执行用例 |

## 按对象补充检查（适用时）

| 对象特征 | 补充推导 |
| --- | --- |
| 多个可选字段 | 区分各自独立、依赖或互斥；独立字段不能只测全空和全填，还应检查各自单独填写，交互组合按规则与风险选择，不机械穷举 |
| 可修改的配置 | 覆盖首次设置、修改后的业务效果；支持清空时检查清空及回退行为。按已知规则检查新操作与存量对象/会话的影响，未明确的默认值或生效时点保留待确认，不自行增加清空功能 |
| 多对象或多入口 | 先确认关系基数和唯一性作用域，再选关联、共享、隔离及跨入口一致性检查；允许同一父对象关联多个子对象时验证互不覆盖，不能从某字段唯一推断整个关系一对一 |
| 多种来源或分类映射 | 分清输入类型、处理路径、结果分类和展示分类，不从展示类别反推每条路径都支持全部类别。不同来源进入同一操作时，覆盖各来源的资格及实际处理结果；路径确实等价时可用参数组验证 |
| 多规则交互 | 单项覆盖后，补会改变结果的重要组合，如额度与重试、部分成功与后续失败、豁免与保留校验；按明确依据判断优先级、例外条件及仍须满足的约束，不把局部例外扩大为整条流程放行，也不穷举无关组合 |

这些是分析提示，不是每次必增的用例清单；按本次范围选取，并在现有场景中承载相关断言。

## 场景映射与覆盖声明

选定方法后留下简洁设计依据：

`对象/规则 → 方法及理由 → 覆盖目标（类/边界/规则行/迁移/路径） → 用例 ID → 未覆盖原因`

“异常”“P1”“权限”是类型/优先级，不是设计方法。一个方法可产生多条用例，一条用例可承载相关目标，但互不相关的目的不要捆绑。

设计覆盖、规则确认、准备就绪、实际执行、结果通过是不同状态。根据本次选择的目标报告充分性，不要求每个对象套同一组维度；未选的方法不等于漏测，但关键风险未覆盖要解释。

## 跨场景推导示例（仅演示方法，不是默认需求）

### 输入约束

给定：数量必须是 1—100 的整数。等价类包括有效整数、低于下限、高于上限、非整数、缺失；边界取 0/1/2、99/100/101。用 1.5 验证非整数；不要用 1.5 同时验证越界。规则未给定时使用参数而非套用本例范围。

### 多条件优惠

给定：仅会员且订单金额不少于 100 才优惠 10。判定表四类条件组合，金额边界 99.99/100/100.01（金额精度已确认为分）；独立核算优惠和应付值。会员但未达门槛与非会员但达门槛分别覆盖，不能只测满足与全部不满足两条。

### 状态流程

给定：草稿可提交到待审，待审可通过或驳回，已通过不可再次审核。状态迁移覆盖提交、通过、驳回、禁止再次审核；场景法补草稿→待审→驳回→后续处理，后续是否允许修改重提未说明时标待确认，不自动发明。

### 无界面事件

给定：相同事件 ID 重复投递只能入账一次。按数据不变量验证唯一入账与余额增量；按风险分析覆盖连续重复、并发重复、消费重启后重投。不同事件 ID 即使载荷相同应按其独立业务规则处理。不要要求“打开页面点击保存”。

### 只有截图

看到“导出”入口：设计触发导出、结果可取得、导出对象范围一致、无数据与失败恢复，在追踪文件记录推导依据；格式、字段、数量限制和权限未知时参数化/待确认。不能直接指定 CSV 或 10000 行，也不能只检查按钮存在。资料丰富后将已确认部分升级为明确依据。

## 自查

- 所选方法是否针对实际规则结构，而非按页面名称套模板？
- 每条关键规则是否被正向与拒绝条件挑战？复合逻辑是否缺组合？
- 成功结果和副作用是否有观察入口或独立判定依据？
- 失败发生在提交前、已提交但响应丢失、恢复后，是否存在不同结果？
- 未知参数是否影响仅一个分支，却被错误扩大成整个功能无法设计？
- 代表值是否真的属于声明的类，数据是否会被更早的校验拦截？
- 用例集合是否存在相同目的的重复，却漏了状态、时序或数据隔离？
