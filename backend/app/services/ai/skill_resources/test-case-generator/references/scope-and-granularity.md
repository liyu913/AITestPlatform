# 需求类型、范围与用例粒度

先判断需求改变了什么，再选择覆盖范围。材料形式（文档、原型、截图、接口）与需求类型分开判断，不能因为只有截图就默认新增，也不能因为一次用户要求精简就把所有任务按优化处理。

| 需求类型 | 识别依据 | 默认覆盖 |
| --- | --- | --- |
| 新增功能 | 原来不存在的新能力或业务流程 | 新流程端到端、主要分支、输入边界、失败恢复、权限与关联旧功能 |
| 功能优化 | 原行为存在，支持范围、规则、交互或效率发生调整 | 新旧差异、改变的规则、受影响旧行为、关键失败路径；旧链路取代表性回归，不重建全系统测试集 |
| 缺陷修复 | 有可复现问题及预期修复行为 | 原复现条件、修复后结果、根因相关边界和相邻路径；未明确根因时不虚构 |
| 混合需求 | 同文档包含新增、修改和修复 | 按功能点分别分类和展开，汇总时合并共同准备与重复回归 |
| 类型未知/仅有成品截图 | 无明确新旧基线 | 覆盖本次指定功能及实际操作语义；未知规则保留条件场景，不假定全站重测 |

在设计说明或追踪scope中用几句话记录类型依据、核心范围、关联回归和补充范围。简单任务不必额外输出复杂变更矩阵；优化需求可用“原来→现在→受影响行为”三项梳理。

## 分配测试层级

默认核心套件面向本次功能验收，写用户可执行的动作和明确结果。接口功能本身就是需求时，接口步骤就是核心，不能强行改写为页面操作。

必须保留：明确验收规则、主流程、独立业务分支、关键拒绝条件，以及可能导致错账号、错误内容、越权或丢数据的直接风险。

实现层细节（缓存键、HTTP调用次数、内部事务、极端并发等）按需求和风险选择。若属于明确要求但不适合混入日常手工套件，可放单独补充检查：写明依据、目标、观察方法、结果标准和未执行状态。用户要求全量/专项时展开为对应套件，不用“精简”漏掉要求。不能把补充检查当成已完成测试。

无关专项不主动扩展。缺少测试环境不是移走核心用例的理由；保留所需准备规格。危害重大的安全或一致性规则即使需接口支持也应在核心或明确专项中有实际用例。

## 合并和拆分

- 可合并：验证目的、前置状态/触发时机、规则及结果判断均相同，操作路径等价，只有同等价类输入不同。例如已明确不支持的协议用http/git/ssh参数组，逐个执行并分别记录结果。
- 应保留或拆分：独立规则、关键初始状态、时序或恢复机制不同，即使最终结果相同也不能按措辞去重。例如锁定后首次访问，与先打开旧页面再跨过锁定时点提交，分别验证当前访问限制和旧会话提交校验。
- 单点与端到端用例按目的比较：端到端若验证跨节点状态传递、关联或一致性，保留其独立目标；若只是重复相同步骤和断言则合并。部分断言重复时收敛重复部分，不删除承载其他独立规则的整条用例。
- 参数组逐项列数据及对应预期，不用“各种异常”“全部边界”代替数据；不把30个无关检查藏在一行来制造条数减少。
- 参数组逐组重置数据，一个参数组失败不阻止其他独立组执行；编号遵循 [编号与对应关系](test-design.md#编号与对应关系)。
- 保留已有用例ID；合并后保留主用例ID，在追踪文件记录吸收的ID。移出核心的条目记录去向，不能把它们统计为核心覆盖。

不固定20条、25条或任何数量上限。规模由独立规则、变更范围和风险决定；数量明显超过功能复杂度时先查重复、层级混杂和过度组合。

## 对照示例

- 新增扫码登录：验证扫码、确认、取号、新老账号匹配、授权拒绝及登录态隔离，不能只测按钮出现。
- 优化文件导入：重点测新增支持的来源、解析规则、歧义处理及原有来源回归；内部机制是否覆盖由明确要求和直接风险决定，步骤直接描述动作与结果，不按前后台或接口分工。
- 修复重复提交：重现重复条件、验证仅一次业务结果、检查失败后重试；无需重做所有正常表单输入。
- 截图含“下架”：设计下架成功与失败/状态限制；未展示确认弹窗时保留条件分支，不凭截图断言一定存在。
