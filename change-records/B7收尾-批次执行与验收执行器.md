## 3. 第一版验收执行器（B7 收尾）

`backend/tools/acceptance_first_release.py`（CLI + 可导入模块）：

```bash
cd backend
uv run python tools/acceptance_first_release.py --dry-run          # 只打印 60 项范围
uv run python tools/acceptance_first_release.py \
  --base-url http://127.0.0.1:8000 --username admin --password admin123 \
  --run-api --run-ui --out ../logs/acceptance
```

行为：

1. 登录并幂等准备项目、API/Web 环境、需求（默认 10 个，验收规则）、60 条用例（20 手工 + 20 接口 + 20 Web）；
2. 建计划与批次（目标构建、环境快照、凭据引用、数据说明），60 个计划项入批次并指派给当前用户；
3. 手工项按 `--known-defects`（默认 6）登记为失败、其余通过，摘要明确标注「验收人工执行」；
4. `--run-api/--run-ui` 时逐项启动执行并等待同步结果，未开启则记录为未执行；
5. 对失败项建缺陷并走「复测通过 → 关闭」的闸门；
6. 生成批次报告，读取快照，按验收表逐项判定，输出 `acceptance-<时间>.json`。

判定项（任一不满足即 `incomplete`，退出码 1）：范围数、手工记录数、自动执行数、已知缺陷关闭数、需求覆盖率 ≥90%、报告快照存在、结果分桶守恒。

手工结果是测试人员判定的录入，脚本在摘要里明确标注，不冒充平台自动执行；自动项未执行时脚本判为「未完成」而不是通过。

确定性验证：`tests/test_acceptance_tool.py` 用 `httpx.MockTransport` 搭建有状态假后端，跑完整流程（建范围→执行→缺陷→报告→判定），并覆盖「未开自动执行必须判未完成」「错误范围/无覆盖必须失败」「dry-run 不联网」。
